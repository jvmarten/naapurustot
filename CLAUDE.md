# CLAUDE.md

## Project overview

naapurustot is a static React + TypeScript map application for exploring postal-code-level statistics across all of Finland — 3,018 postal-code areas in 69 sub-regions (seutukunnat) — and all of Sweden: 6,160 SCB DeSO areas in 71 FA25 regions (`docs/SWEDEN_EXPANSION.md`). Live at naapurustot.fi, served from the DigitalOcean droplet by Caddy (see "Where the site is served"). The frontend runs entirely in the browser from pre-built TopoJSON/JSON assets; an optional Express + PostgreSQL backend (`server/`) adds accounts and sync of favorites/shortlist/notes/preferences. The app works fully without it.

```bash
npm run dev            # Start dev server (Vite, port 5173)
npm run build          # TypeScript check + production build → dist/
npm run test           # Run tests (Vitest, jsdom)
npm run test:watch     # Vitest in watch mode
npm run test:coverage  # Tests with v8 coverage
npm run coverage:check # Coverage ratchet vs coverage-baseline.json (CI gate)

npm run lint           # ESLint
npm run preview        # Serve production build locally (port 4173)

npm run build:pages    # Pre-render profile/hub pages + sitemap (Node 22.18+)
```

## Architecture

- **Framework:** React 19, TypeScript 5.9, Vite 8
- **Map:** MapLibre GL JS with lazy-loaded Turf.js modules for geospatial calculations
- **Styling:** Tailwind CSS 3
- **State:** React hooks + Context (theme). No external state library. Tooltips use an external store (`tooltipStore.ts`) to avoid 60 Hz re-renders.
- **i18n:** Finnish (default), English, and Swedish. Translations live in `src/locales/{fi,en,sv}.json` (flat keys, parity enforced by a test). Use `t('key')` from `src/utils/i18n.ts`; `React.memo` components calling `t()` must also call `useI18nVersion()`. en/sv are lazy-fetched assets — never import them statically (bundle budget).

### Key directories

- `src/components/` — React components (Map, NeighborhoodPanel, LayerSelector, Legend, SearchBar, panels, dropdowns; `profile/` for profile-page parts)
- `src/hooks/` — 25 custom hooks (data loading, localStorage+server-synced user state, URL state codec, gestures)
- `src/utils/` — Data layers (`colorScales.ts`, 76 layers), metric definitions (`metrics.ts`), quality index, regions (69 Finnish + 71 Swedish `se_*`, the latter generated into `regionsSe.ts`), area ids (`areaId.ts`), similarity, filtering, formatting, i18n
- `src/locales/` — Translation JSON files (fi.json, en.json, sv.json)
- `src/__tests__/` — 170+ Vitest test files (jsdom)
- `src/data/` — **What the app actually loads** (generated by `npm run build:data`): `regions/*.topojson` (69 + 71 per-region files), `region_outlines.topojson` (both countries' region outlines; built from `seutukunnat.topojson` + `scripts/se/fa25_outlines.geojson`), `region_properties.json` (all 3,018 + 6,160 areas, geometry-stripped), `national_ranges.json`, plus adjacency/coverage/grid manifests
- `public/data/metro_neighborhoods.geojson` — Pipeline output (~39 MB), source of truth for `build:data`; **build input only** — it is stripped from `dist/` at build time and never fetched by the app
- `scripts/prepare_data.py` — Python data pipeline that rebuilds the GeoJSON
- `scripts/se/` — Sweden's pipeline: `fetch_se_boundaries.py` (SCB DeSO/RegSO, Tillväxtverket FA25), `fetch_scb_deso.py` (SCB tables), `build_se_geojson.py` → `public/data/se_deso.geojson` (Sweden's build input, stripped from dist like the Finnish file), `src/utils/regionsSe.ts` and `scripts/se/fa25_outlines.geojson`

## Data integrity

**All data must come from real, verifiable sources.** Never generate, fabricate, or use placeholder/fake data — not in the GeoJSON dataset, not in the data pipeline, and not as temporary stand-ins. If real data is not yet available for a metric or area, leave it out entirely rather than filling in synthetic values. Every value shown on the map must trace back to an actual data source (e.g., Statistics Finland, HSL, Helsinki Region Infoshare, OpenStreetMap).

**Always propagate data into the GeoJSON.** When adding or updating any data layer, verify that the values are written into `public/data/metro_neighborhoods.geojson` — the file `build:data` reads — not just the intermediate JSON in `scripts/`. After updating data, confirm the GeoJSON property values match the new data, then run `npm run build:data` so the change reaches the `src/data/` artifacts the app loads. This step must never be skipped.

## Data granularity

We want the lowest-level data possible. The minimum acceptable granularity is **postal code level**, but whenever a data source offers finer resolution (e.g., 250 m × 250 m grid cells, building-level, block-level, or coordinate-level data), prefer and integrate that instead (see the grid overlays: air quality ~250 m, light pollution ~500 m). When evaluating new data sources or extending existing ones, always check whether a sub-postal-code breakdown is available. Municipality-level values distributed to postal codes must be flagged `is_proxy` in `src/data/data_sources.json` (validation enforces this).

## Git workflow

**Do not create pull requests.** Push your changes to a `claude/*` branch and let the auto-merge workflow (`.github/workflows/auto-merge.yml`) handle merging to main after CI passes. Never open a PR manually or via API. Note: pushing a second `claude/*` branch cancels an in-flight auto-merge run (shared concurrency group) — serialize or stack branches.

### Another session may be working in this directory right now

More than one Claude session is often open on this repo, and they share one working
directory, one git HEAD and one `node_modules`. Assume you are not alone:

1. **`git status` before `git checkout`, `git pull` or `npm install`.** If the tree holds
   work you did not create, it belongs to another session. Checking out moves HEAD under
   it; `npm install` empties `node_modules` under whatever it is running.
2. **Push with an explicit refspec: `git push origin HEAD:claude/your-branch`.** Bare
   `git push` has pushed the *other* session's branch.
3. **Stage by explicit path**, never `git add -A` / `git commit -a`, or you will sweep up
   files that are not yours.
4. **If the directory is occupied, work in a worktree** — create it for the task, remove
   it when done. Do not maintain a permanent one; sessions outlive nothing.
   ```bash
   git worktree add C:/code/naapurustot-<task> -b claude/<task>
   # only if you need to build/test there:
   cmd //c mklink /J node_modules C:\code\naapurustot\node_modules   # or npm install
   ...
   git worktree remove C:/code/naapurustot-<task>
   git worktree prune          # clears worktrees left by sessions that died
   ```
   The junction re-shares `node_modules`, so it does not protect against a concurrent
   `npm install` — use a real install when you care.
5. **Serialize pushes — check the queue first.** A worktree does not help here: the
   auto-merge concurrency group is shared, so a second `claude/*` push cancels the first
   branch's in-flight run. Land one, wait for green, then push the next. Do not guess
   whether the coast is clear; ask:
   ```bash
   npm run queue:check            # exit 0 clear · 1 auto-merge in flight · 2 wedged deploy
   npm run queue:check -- --wait  # block until the in-flight auto-merge finishes
   ```
   Run it immediately **before** every `git push`. Exit 1 means a push right now silently
   cancels somebody else's merge.
6. **Verify the merge landed — a green run is not proof.** Check
   `git merge-base --is-ancestor <your-sha> origin/main`. An auto-merge run has reported
   `completed success` while its branch was cancelled and deleted without merging.

After any interruption (a crashed build, a wiped `node_modules`), **re-run
`npm run build:data` before committing.** `build_region_data.mjs` shell-redirects
`geo2topo` output, so a run killed at that moment leaves a **0-byte** `<region>.topojson`
and an orphaned `<region>.geojson` temp file. That has shipped. Verify *all* artifacts,
not a sample:

```bash
find src/data public/data -type f \( -name "*.json" -o -name "*.topojson" \) \
  | sort | xargs md5sum > /tmp/a.txt
npm run build:data && find src/data public/data -type f \( -name "*.json" -o -name "*.topojson" \) \
  | sort | xargs md5sum | diff /tmp/a.txt -
```

### Post-push: verify the auto-merge run (do this every push)

Pushing is not "done" — the merge only lands if all auto-merge jobs (`security`, `checks`, `e2e`, `lighthouse`, `server`) pass. There is no PR and no webhook for branch-push CI, so you must check the run yourself and drive it to green:

1. **Poll the run.** `mcp__github__actions_list` → `list_workflow_runs` for `auto-merge.yml`, `workflow_runs_filter.branch = <your claude/* branch>`. Read `status`/`conclusion` of the newest run (re-poll until `status: "completed"`).
   The GitHub MCP is **not always present** — fall back to `gh`, which is always available:
   ```bash
   gh run list --workflow=auto-merge.yml --branch=<branch> --limit 3 \
     --json databaseId,status,conclusion,headSha
   gh run view <run-id> --json status,conclusion,jobs      # per-job breakdown
   gh run view <run-id> --log-failed                       # logs of the failed job
   ```
   Do **not** use `gh run list --template` — it mangles run IDs. Use `--json` and parse.
2. **`conclusion: "success"`** → normally the merge landed and the branch was auto-deleted.
   Confirm it rather than assuming: `git fetch -q && git merge-base --is-ancestor <sha> origin/main`.
   A run has reported success while its branch was cancelled and deleted *without* merging.
3. **`conclusion: "failure"`** → `mcp__github__get_job_logs` with `run_id`, `failed_only: true`, `return_content: true` (or `gh run view <id> --log-failed`). Diagnose, fix on the same branch, re-push, and repeat from step 1 until green (re-pushing the *same* branch is safe; pushing a *different* `claude/*` branch cancels the in-flight run). If a failure is genuinely out of scope or you're stuck after a couple of rounds, stop and report the diagnosis instead of looping.

If you watch the run with a `Monitor`, make the filter emit on **failure states too**, not
just job successes — a monitor that only greps for green stays silent through a failed run
and its silence is indistinguishable from "still going". Two such monitors timed out at an
hour here while the run had already failed.

**`jq` is not installed on this machine.** Use `gh`'s built-in `--jq` instead; a monitor
that pipes to standalone `jq` emits nothing *and* never sees its own exit condition, so it
runs until timeout looking exactly like a job that is still going. Three monitors were lost
to this in one session.

```bash
gh run view <id> --json status,conclusion,jobs \
  --jq '"RUN: \(.status) \(.conclusion)", (.jobs[] | "  \(.name): \(.conclusion)")'
```

The container is ephemeral, so verify within the session that produced the push. **Known recurring failure modes:**

- **`security` — `node scripts/check-audit.mjs` / `… server/api`** (`npm run audit:check` locally; run for both trees): a transitive high-severity advisory. Fix by pinning the offending package in that tree's `package.json` `overrides` to the first patched version *within its parent's compatible major* (e.g. `"undici": "^7.28.0"` to satisfy jsdom's `^7.x`), then `npm install` and re-run the gate. Don't jump a major (it can break the parent) — and when the patch exists only in a later major, verify the parents can load it before forcing it: `brace-expansion@5` needed `"minimatch": "^10.2.5"` alongside it, because `minimatch@3` does `require('brace-expansion')` as a callable and v5 exports a namespace. Moderate-only advisories don't fail the gate. If a high advisory genuinely cannot apply to this codebase and its only fix is a major bump, add a reviewed entry to `ALLOWLIST` in `scripts/check-audit.mjs` with the reason, the `scope` (`.` or `server/api`) and an `until` date — the gate fails once an exemption expires, so it can't become permanent.
- **`checks` — build:data idempotency gate**: re-running `npm run build:data` must reproduce committed `src/data`/`public/data` byte-for-byte. A diff means a generator is non-deterministic — it must derive any timestamp/vintage from committed source data, never `new Date()`/`Date.now()` (e.g. the planning snapshot is read from `scripts/planning_raw/snapshot.txt`, stamped by the fetch scripts at fetch time). Fix the generator; only commit a regenerated artifact when the source data genuinely changed.

### Where the site is served

`naapurustot.fi` and `www` resolve to the droplet, where Caddy serves
`/srv/naapurustot/current` (`server/caddy/Caddyfile`; `SITE_HOSTS` in the droplet's
`server/.env` picks the address). `deploy.yml` ("Deploy site") is one job: build, prerender,
rasterize cards, then rsync into a new release folder and switch `current`. "Is it live"
means that run succeeded; on failure it opens an issue and the droplet keeps serving the
previous release (the five newest are kept, so a rollback is re-pointing `current`).
`deploy-server.yml` ("Deploy Server") is a different thing — the backend API, run only when
`server/**` changes — so its going quiet says nothing about the site.

**There is no GitHub Pages standby any more** (dropped 2026-10-28, `docs/ARCHITECTURE.md` →
Hosting). Its deploy shared a concurrency group with the droplet's, so a Pages environment
that never started — a job waiting on an environment has not begun, so `timeout-minutes`
never ticks; one sat 1 h 44 m — held every later deploy, live site included. Do not bring
it back as a second publish in the same workflow. `npm run queue:check`'s exit 2 ("wedged
deploy") detects that Pages-era state and should no longer occur.

## Known pitfalls

### Bundle budget

`scripts/check-bundle-size.mjs` enforces **two** budgets (both in `ci.yml` and `auto-merge.yml`); either one over fails the build.

### Density metrics: 4 decimals, never 1

Per-km² metrics are stored at 4 decimals (`prepare_data.POI_DENSITY_DECIMALS`, mirrored in `fetch_lipas.py`, `fetch_ev_charging.py`, `fetch_transit_stops.py` and `METRIC_DEFS`). At 1 decimal anything below 0.05/km² becomes exactly `0.0`, and the median Finnish postal area is 52 km² — so one real facility rounds away across three-quarters of the country (this shipped for months: 3,169 false zeros). The five service layers also carry a raw `*_count`; `validate_data.py` hard-fails on a positive count with a zero density. See `docs/ARCHITECTURE.md` → "Density precision".

A partial national fetch must never be written. `_overpass_query` rejects responses carrying a `remark` (Overpass reports server-side timeouts as HTTP 200), `_overpass_query_all_regions` aborts if any of the 69 bboxes is unfetchable, and `fetch_lipas.py` retries then raises rather than writing a truncated page walk. Every one of these guards exists because the alternative silently shipped as measured zeros.

### Server env vars must be listed in docker-compose.yml

The API reads `process.env` directly (no dotenv), so a variable in the droplet's
`server/.env` reaches the container only if `server/docker-compose.yml` names it under the
`api` service. The Lightning tier and the AI assistant sat silently disabled in production
for exactly this reason. `server/api/src/composeEnv.test.ts` now fails when code reads a
variable compose does not pass; if you add an indirect reader like lightning.ts's
`envInt('NAME')`, add its pattern to that test.

### `tsc -p tsconfig.json` checks nothing

The root `tsconfig.json` is a solution file — `files: []` plus `references` — so
`npx tsc --noEmit -p tsconfig.json` exits **0 in under a second having compiled
zero files**, which is indistinguishable from a clean typecheck and is how a
`TS18047` reached CI and turned a run red. Use what CI uses: `npx tsc -b`
(or `npm run build`, which begins with it). Add `--force` when you want to be
sure the incremental build info is not answering for you.

### Prerender head-token regexes

`scripts/prerender.mjs` clones `dist/index.html` using first-match regexes over `<title>`, `<noscript>`, and `</head>`. Never put those tokens in index.html's head — even inside comments — or all ~9,000 prerendered pages silently corrupt. Run `npm run build:pages` to catch it.

### Social-card cache: two invariants, or the deploy dies

`deploy.yml` caches `dist/og` across deploys (rasterizing ~9,261 cards takes minutes) with a
`restore-keys: og-cards-` prefix fallback. That cache **ratchets** unless both hold:

1. `prerender-hubs.mjs` deletes every cache-restored `*.svg` before emitting this build's set.
2. `rasterize-cards.mjs` deletes the SVGs once the PNGs exist (they are inputs — the HTML
   references the `.png`, and nothing in `src/` fetches `/og/*.svg`).

They interlock: the orphan prune in `rasterize-cards.mjs` deletes a PNG only when no SVG of
that content-hashed name remains, so **one surviving stale SVG shields its stale PNG forever**.
With both broken the tree hit 2.4 GB / ~65,000 files (32,538 in `dist/og` against ~9,000 real
cards). It failed silently — the `deploy` dist-size guard was warn-only — until the (then) Pages
sync crossed `actions/deploy-pages`' 10-minute default timeout. The droplet sync has no such
timeout, so a ratcheting tree now shows up only as a slower sync and a fuller disk — the
`check-dist-size.mjs --profile deploy` gate is what catches it; keep the tree small.

A third, separate constraint governs how the cards are *rendered*. Batches run one per core,
and each child costs ~200 MiB fixed plus ~3 MiB per card (a 1200×630 RGBA pixmap
`@resvg/resvg-js` never hands back). The fixed cost does not divide across workers, so the
batch size scales **down** as concurrency scales up, holding the total peak at ~1.4 GB —
**raising concurrency without shrinking the batch re-creates the OOM that made the batching
scheme necessary in the first place.** A cold pass is ~3m50s on the 4-vCPU runner (it was
~14m30s when the batches ran sequentially on one core) against the build job's 30-minute cap.

### All-Finland view: region borders

The all-Finland view (`?city=all`, the default) shows seutukunta outlines, not individual postal-code borders. This has broken repeatedly — do not re-introduce these issues:

1. **Region outlines are pre-baked** into `src/data/region_outlines.topojson` (`scripts/build_region_outlines.mjs` in `build:data` merges Finland's `seutukunnat.topojson`, built by `scripts/build_seutukunta_boundaries.mjs`, with Sweden's `scripts/se/fa25_outlines.geojson`) and lazy-fetched at runtime by `src/utils/metroAreas.ts`. Runtime no longer uses `@turf/union` (the `package.json` dependency is vestigial). The degraded fallback while outlines load is raw MultiPolygon concatenation, which preserves internal postal borders — `ensureOutlinesLoaded` must keep resetting its promise on fetch failure *and* on an empty parse, or the view locks onto the fallback permanently.
2. **The `metroAreaCache` must invalidate when outlines become available.** The cache records a `usedOutlines` flag — if it was built with the fallback before the outlines fetch resolved, it must be rebuilt once they are ready. Do not remove or simplify this check.
3. **Both `Map.tsx` and `SplitMapView.tsx` must filter out postal-code borders for region features** using the `_isMetroArea` property: `METRO_LINE_LAYER` draws only the outer region boundary; the regular `LINE_LAYER` (and the no-data hatch layer) must exclude `_isMetroArea: true` features.
4. The all-cities dataset (`loadAllData`) has `geometry: null` on every feature — code that assumes geometry there (flyTo, centroids) must guard for it; national-scope features navigate to profile pages instead of flying the map.

### MapLibre

- Never replace a state-dependent paint expression with a constant (`setPaintProperty`) — the next `setFeatureState` throws. Hide layers via `buildFillOpacity(0)`.
- The postal fill's opacity is a zoom curve (close-zoom easing, `src/utils/fillOpacity.ts`), so its buckets hold composite binders: a zoom-less feature-state `case` set on it throws the same way. Build every fill-opacity through `withCloseZoomDamping`. And a zoom `interpolate` nested inside a `case` is rejected by validation — the layer silently keeps its old value (`buildFillOpacityFadeOut` has that shape and never applies).
- Gate post-init layer work on the persistent `mapStyleLoadedRef`, not `map.isStyleLoaded()` (returns false during in-flight `setData` re-parses, silently dropping work).

### /live/ shadows

1. **The map is pinned to `maxPitch: 0`.** The overlay re-projects footprints with an affine Mercator→screen transform calibrated from three `map.project()` calls — four multiply-adds per vertex instead of a projection call, which is what lets a city-zoom view of ~10,000 buildings render and scrub. That transform is exact only at pitch 0. Allowing pitch silently skews every shadow.
2. **Every ring fed to the emitter must wind the same way.** `projectPrepared` normalises orientation *after* simplification, because dropping vertices can flip a near-degenerate ring's sign — and one ring winding the wrong way subtracts itself from the nonzero-fill union, which renders as a hole rather than as an error.
3. **The city model and OSM are combined, never chosen between.** A viewport reaching past a shard's rectangle takes measured heights inside it and queries Overpass only for the strips around it (`bboxSubtract`). Selecting a single source by the viewport centre is what made buildings stop along an invisible straight line. The Overpass budget (`MAX_OSM_AREA_KM2`) is charged against those strips, not the whole viewport.
4. **Sunset is "shade everywhere", not "no data".** Below the horizon the layer fills the whole canvas, ramped to full night at −6°. Drawing nothing says "we have no buildings here" in the same visual language as a failed fetch.
5. **Never call `closePath()` in the shadow emitter.** `fill()` closes subpaths implicitly, and Chromium's `closePath` cost grows with the path already accumulated — one `Path2D` holding tens of thousands of subpaths goes quadratic. A CPU profile of a city-zoom scrub put **96.7 % of all JS time** inside `closePath`. Removing it was byte-identical on canvas (same painted pixels, alpha sum and hash) and took a scrub step from 3,546 ms to 246 ms at z13.5. `paintBuildings` closes only when it will `stroke()` (z ≥ `OUTLINE_ZOOM`), because stroking an open ring leaves a gap. If you need a stroked path, build a separate small one.
6. **Detail is a zoom ladder, not a constant** (`simplifyPxForZoom`). At Finland's latitude ground resolution is ~78,271 / 2^zoom m/px, so a 20 m building is ~2 px at z13 and ~17 px at z16. Below z15 the outline's shape carries no information — only mass and shadow direction — so the tolerance is raised until `projectPrepared` collapses footprints to their bounding box. That ladder is what takes z13.5 from 246 ms to 62 ms; measure before widening it.
7. **Trees are cast too, from HSY canopy** (`scripts/fetch_hsy_canopy.py`). Each polygon carries `korkeus_ka_m`, a measured MEAN canopy height — use that, not the layer's band label: sampling 400 per band showed the mean tracks the bands (5.6 / 10.6 / 13.7 / 18.3 m medians) but sits below them, because the band is the dominant class. Canopy sweeps into the SAME path as the buildings, at the same tone, and is skipped below the single `DETAIL_MIN_ZOOM` of invariant 10 — where a 10 m crown is about one pixel and cost 62 → 106 ms a scrub step for an even wash. (This line named a `CANOPY_MIN_ZOOM = 14` for a while. No such constant exists or should: invariant 10 is the record of what a second, canopy-only threshold did to the map.) Helsinki's `Puurekisteri_piste` (64,533 individual trees) is NOT usable: its size field is trunk diameter, with no height and no crown radius.
8. **The two WFS servers disagree on axis order.** `kartta.hel.fi` (3DCityDB, buildings) wants BBOX as *east,north*; `kartta.hsy.fi` (canopy) wants *north,east*, both in EPSG:3879. Getting it wrong returns HTTP 200 with zero features — indistinguishable from "there is nothing here". The same tile returned 0 one way and 617 the other.
9. Fetches are padded past the viewport (`fetchPadMetres`) so off-screen buildings still cast into view, and the loaded bbox + plan are cached so a zoom-in or short pan reuses them. Padding is paid for on all four sides — a 15 % margin is ~35 % more query area. Note `MAX_SHADOW_PAD_METRES` (2 km, query area) is deliberately NOT `MAX_SHADOW_METRES` (12 km, drawn length) — they answer different questions, and growing the pad to match the clamp makes a low-sun viewport ask for hundreds of km² and be refused, turning "longer shadows" into "no shadows".
10. **Detail is one floor for buildings AND canopy, governing both the fetch and the draw** (`DETAIL_MIN_ZOOM`). Two thresholds is how a viewport ends up holding ~43,000 footprints and crowns that the renderer then sweeps every frame at a zoom where none of them covers a pixel — that shipped, and the map stalled. The sub-pixel cull does **not** bound this: it drops a caster only when the footprint *and* its shadow are sub-pixel, and near sunset a 12 km shadow is tens of pixels long however small the thing casting it. Below the floor, terrain is what draws.
11. **No free DEM tile source sends CORS.** `s3.amazonaws.com/elevation-tiles-prod`, its dualstack and `/v2/` paths all answer 200 with no `Access-Control-Allow-Origin`, so a browser can never read their pixels — the canvas taints and `getImageData` throws, and a bare `fetch` is blocked. That applies whoever issues the request, MapLibre's own `raster-dem` source included. This is why the terrain pyramid is mirrored at build time (`scripts/fetch_terrain_dem.py`) and served same-origin, and why it cannot be "simplified" into a runtime tile URL.
12. **Terrain tiles must stay OUT of the PWA precache.** `globPatterns` in `vite.config.ts` matches by extension, and the pyramid is PNG, so it swept all 265 tiles in and took first-visit cost from 2.3 MB to 11.9 MB — paid by every visitor, not just the ones who open `/live/`. `globIgnores: ['**/data/terrain/**']` holds it back; check `precache N entries` in the build output after touching anything under `public/data`.
13. **Every caster merges into ONE mask before compositing, and ONE TONE comes out.** Filling shade straight onto the canvas per source alpha-composites the overlaps, so ground under both a tree and a building came out at 0.408 against a 0.278 building tone — a 1.465× dark patch, which is not an optical effect (a second occluder behind the first changes nothing). Every caster now goes on the mask **opaque** so they saturate, then one `drawImage` at `shade.day`. Adding a new caster means adding it to that mask, not adding a fill — and adding it at full opacity: a caster drawn at a fraction is the one thing that can still accumulate under a partially-covered neighbour. Canopy used to be that caster, at 0.65 for "a crown dapples, a wall blocks". The union was exact even then (measured in Chromium: overlap alpha 71 = building alpha 71, light theme), but two tones make the *intersection* a visible third shape, which reads as shadows adding up — and simultaneous contrast against the lighter tone makes it read strongest exactly where the casters meet. Buildings and canopy therefore share one `Path2D` and one `fill`, which also drops the mask entirely for a city viewport with no relief or terminator on it.
14. **The sun is a FIELD over the map, not a number.** `sunPosition(when, centre)` describes the centre pixel and nothing else. A camera framing Finland spans ~2,000 km: at 02:18 UTC on 2026-08-12 the real altitude ran from **−12.9° over Denmark to +8.5° over the White Sea**, and shading all of that with the centre's −1.6° drew the entire continent as one flat sheet of night — no terminator, no relief, the exact "zoomed out looks wrong" report. `solarFrame`/`frameAltitude` (`src/utils/sun.ts`) hoist the instant-dependent terms so altitude can be asked at thousands of points for four trig calls each; `twilightLayer` samples it on an 8 px screen lattice and `terrainShadowMask` resamples it per swept cell. **The 8 px lattice is set by the terminator, not by the field** — everything else here would be happy at 64 px, but bilinear interpolation of a step reconstructs the edge *on the lattice*, so a coarse spacing draws the day/night line as a visible staircase. What is still a single value is the shadow BEARING: the O(1) sweep exists because every ray is parallel, so bending them per cell would curve the traversal and start missing cells. The residual (~30° of azimuth across a continental frame) is a soft error in a soft-edged layer — do not "fix" it by making the sweep per-cell.
15. **Sunset is a two-pass wash, because night is darker than a shadow.** Night reaches `shade.night` (0.62) while a daytime shadow is `shade.day` (0.45), and the merged mask composites at ONE alpha — so the wash cannot live on it as a single value. `twilightLayer` returns `shade` (opaque past sunset, joins the mask and *saturates* against relief and walls, holding invariant 13) and `deepen` (the remainder, `(nightAlpha − day)/(1 − day)`, drawn after the mask). `deepen` is zero wherever the sun is up, so it can never darken a daytime shadow. Do not collapse these into one fractional-alpha layer: source-over accumulates, and a fractional caster over relief gives 0.90 where the union wants 0.73.
16. **The DEM pyramid is TIERED, and ground outside it is not "flat" — it is unknown.** `loadHeightField` zero-fills a missing tile, which is indistinguishable from measured sea level to everything downstream: a Finland-only pyramid rendered Norway as a flat, fully-lit plain with a straight-edged seam where coverage stopped. `ZOOM_BBOX` in `fetch_terrain_dem.py` therefore widens as the level coarsens — z3–z6 continental, z7 regional, z8 Finland — because the camera picks the level and a country-wide camera sees Norway while a street-corner one does not. Coarse coverage is nearly free (one z4 tile covers 256 z8 tiles); the whole pyramid is 603 tiles / 20 MB. Re-running the fetch is deterministic (z8 came back byte-identical), and it must stay **out of `build:data`** (it reaches the network) and out of the PWA precache.
17. **`selectTerrainLevel` spends the whole tile budget — and asks about COVERAGE at both ends.** `terrainZoomFor` targets ~2 levels below the camera, which is right for a shadow's soft EDGE and wrong for its CASTER: at a continental camera that picked ~4.6 km cells, and Finnish relief is 50–200 m over a few km, so the hills were averaged flat before the sweep saw them and the sunlit half of the map had no relief on it at all. The sweep's cost is bounded by `MAX_TILES × tileSize²` — by the tile COUNT, not the level — so after stepping *down* to fit the budget it steps back *up* while a finer level still fits. **Both loops must test that the level actually holds the viewport**, because invariant 16 made level choice a coverage question and not only a cost one. Gating only the descent is not enough and shipped broken for one commit: a Trondheim camera descends to z6, which covers it, then climbs 6→7→8 into a Finland-only level holding none of it and blanks the layer over the most mountainous ground in the dataset. `selectTerrainLevel` is exported and unit-tested precisely because `loadHeightField` around it needs a network and a canvas.
18. **A heightfield ROW is a Mercator row, not a latitude.** The field is a slab of Web Mercator tiles, so row index is linear in Mercator y and *nonlinear* in latitude — and Mercator's mid-row sits well poleward of the arithmetic mid (66.5°N vs 60.1°N on a continental field). Two things must come through `rowToLat`, and both shipped wrong: (a) the solar lattice, which placed nodes by interpolating latitude linearly while the sweep read them by a linear scale over rows — handing a row up to 6.5° (~720 km) from where it is, turning a real +1.1° sun into −2.6° and declaring sunlit ground to be night; (b) the descent rate, since a Mercator cell shrinks as cos(lat) and `cellMetres` is one sample at the field centre — over 52°N–72°N the true cell runs 1490 m to 740 m against a nominal 1132 m, so shadow LENGTHS came out 32 % long in the Baltic and 35 % short in Lapland. Both errors are one-signed, so neither averages out. `cellMetres` stays on `HeightField` as the nominal figure; the sweep must use the per-row array.

### /live/ realtime feeds

The sidebar is generated entirely from `FEED_GROUPS` in `src/live/feeds.ts`, so a feed is a registry entry plus three locale keys — never a change to `FeedSidebar.tsx`. **Never flip `status` to `'live'` before the feed actually fetches**: a `planned` row renders as a visibly disabled toggle, which is how the page shows where it is going without implying data exists. `sanitizeEnabled` drops persisted ids that are not `live`, so a feed reverted to `planned` cannot come back from localStorage as a toggle nothing responds to.

1. **Trains fetch the whole country, not the viewport** (`src/live/trains.ts`), even though the endpoint takes a `bbox`. The national set is 111 features / 2.4 kB gzipped, so scoping to the camera saves nothing and costs a request per pan plus a beat of latency after every move. Filter at draw time. Don't copy the buildings' viewport-fetch pattern into a feed this small.
2. **Digitraffic answers 406 without gzip.** `Accept-Encoding: gzip` is mandatory. Browsers always send it and cannot override it, so this only bites when probing with `curl` or a Node fetch — where it looks exactly like a broken API. Use `curl --compressed`.
3. **`Digitraffic-User` costs one preflight a day, not one per poll.** It is a custom header on a cross-origin GET so it triggers CORS preflight, but the endpoint answers with `access-control-max-age: 86400`. Fintraffic asks every client to send it; keep it.
4. **Polling stops while the tab is hidden**, and resumes on `visibilitychange` rather than waiting out the interval. This is a page people leave open — an abandoned tab polling a free public endpoint forever is not shippable.
5. **A failed poll keeps the positions already on screen.** Blanking the layer would make one dropped request look like the feed going down; the readout says it failed while the last known state stays drawn.
6. **Feeds draw on the overlay canvas, above the shade — not as MapLibre layers.** The overlay sits on top of the map, so a GeoJSON source renders *under* the shadow fill and under the full-viewport night wash (0.62 alpha), which is where a realtime feed most needs to be legible. `draw()` has ONE exit for this reason; don't reintroduce early returns that skip the feed passes.
7. **Suppress colliding labels, keep every mark.** Trains stack in a terminus throat and unsuppressed labels overprint into one illegible number. `paintTrains` keeps a per-frame list of placed boxes and drops the text, never the dot.
8. **No interpolation between fixes of a measured quantity.** A dead-reckoned dot draws a position nobody measured — the same category as a fabricated data value, on a page whose whole design is about which numbers are measured. `trains.ts` never smooths between polls and `fixAt` refuses beyond half a minute rather than splitting the difference. What IS allowed is drawing a *publisher's own* prediction, differently and never where a measurement exists — see 10 and 11.

9. **The time slider is not a request.** Every measured feed loads its whole DAY up front (`fmiSeriesUrl`/`fetchFmiSeries`) into `timeline.ts`, and the clock samples it locally — a scrub costs a binary search per station and no network. This is not an optimisation, it is what puts these layers on the same footing as the sun: the previous design quantised the instant, debounced it, and fetched, so you had to *stop* the slider before the temperatures belonged to the time under the playhead. A national day of air temperature at hourly steps is ~20 kB gzipped — less than four of the single-instant requests it replaces, against the 288 a full-day drag could ask for. The debounced request that survives only *sharpens* the sample under a rested playhead; nothing on screen waits for it. The radar is the stated exception (15) because a day of it is a thousand times the bytes — but only for ground it has not already decoded: a *second* scrub over the same window costs it no network either.
   - **Every sample carries its own timestamp**, and the panel and readout print it. `sampleTimeline` never averages, never interpolates, and drops a station whose nearest published value is outside the feed's tolerance — absence, which is this project's answer for missing data everywhere else.
   - **A measurement beats a forecast outright, not merely when it is nearer.** Near the top of the hour the forecast run's next step can sit two minutes away while the last actual reading is eight minutes old; taking the nearer put a model's number on a page called /live/ with a station under it.
   - **Do not clear the timeline when a poll is disabled for a future clock.** `useFeedPoll` calls `onClear` when `enabled` goes false, so gating the poll on `!future` discarded the loaded day — forecast half included — the moment anyone scrubbed into tomorrow. Pass `at: null` instead and leave the feed enabled.

10. **Temperature carries into the future; air quality does not, and the difference is the source's.** `ecmwf::forecast::surface::obsstations::simple` takes a bbox and is evaluated at FMI's own observation stations — 189 of 191 matching coordinate for coordinate, which is what lets one station hold a measured morning and a forecast evening in a single series. `fmi::forecast::edited::…::point::simple` answers a bbox with `numberReturned="0"`, which is why the *point* forecast can never be a map layer. FMI's SILAM air-quality forecast is point-only *and* answers `NaN` for `AQIndex`, so that layer stops at the present and says so. Forecast values are drawn in **italic amber**, labelled in the readout, and labelled again in the panel.

11. **Train positions outside the recorded window come from the published timetable, and are diamonds.** `/api/v1/trains/{date}` gives every train's traffic-control points with scheduled times and *measured* passing times where it has already been there (`trainSchedule.ts` prefers `actualTime` → `liveEstimateTime` → `scheduledTime`). Resolved through the station register that is a route through the day, and a position between two points is interpolation along it — so the mark is never the measured feed's circle in either of its states, the readout names the source, and the panel names the two control points and whether their times are measured. Measured always wins: live poll, then the session's recorded snapshots, then this. Median gap between consecutive points is 1.9 km (p90 11 km, max 44 km), which is why the segment is printed rather than implied. It costs 638 kB gzipped a day, so it is fetched only when the clock lands somewhere nothing measured can answer for, debounced, and cached per date (two at most).

12. **Lightning is EVENTS, so the clock asks it a different question — and the window is part of the feed.** Every other measured layer here is a station with a state, and `sampleTimeline` asks "what were you showing at T". A flash lasts a fraction of a second, so the same question is empty essentially always; `lightning.ts` answers "what struck between T−30 min and T" instead, and the readout states that window in words in *every* arm, because "17 strikes" says nothing until you say over how long. Marks fade with their own measured age, which is what makes half an hour of them read as a cell moving; nothing is interpolated and nothing is drawn outside the window. `cloud_indicator` is 0 for a ground flash and 1 for a cloud flash — FMI's metadata does not say so, and it was established from 39,755 strikes (ci=1 has multiplicity exactly 1 always, median |I| 5 kA, 27 % negative; ci=0 has multiplicity 0–7+, median |I| 12 kA, 89 % negative — the textbook signatures).

13. **`multipointcoverage` beats `simple` for events, which is the opposite of the rule for stations.** `observations.ts` measured the two encodings and chose `simple` because gzip eats the verbose form's repetition. That conclusion is right for a couple of hundred stations and wrong by two decimal orders for tens of thousands of point events, because `simple` emits a full GML element *per parameter per record*: the same 24 h of Finnish strikes is 1.5 MB raw / **387 kB gzipped** as a coverage and 75.6 MB raw / **2.0 MB gzipped** as `simple`. Measure the encoding against the shape of the data, not against the last feed. A day of lightning is ~10 kB on a median day and 554 B in winter; the 477 kB storm day is why the feed is `defaultOn: false`. It is also the one day feed with **no `dayEpoch` refresh** — there is no forecast half to go stale and the measured past does not change, so the tail poll is the whole of what needs refreshing.

14. **A failed POLL is not a failed DAY, and they must not share a state.** The two requests cover different spans — the day is the whole day, the poll is a window — and an archive poll fires **once** and never retries (`useFeedPoll` stops rescheduling when `at` is set). Sharing one tri-state meant a scrub to yesterday 06:20 that loaded ~190 stations successfully and then lost its single refinement request replaced the count with "Could not load temperature observations", permanently, over a map full of correct readings. Each feed carries `day` and `pollFailed` separately: a failed day replaces the layer's sentence, a failed poll appends a note to it. The poll's failure raises the collapsed chip only while the page is following real time, because scrubbed it is a refinement of something already drawn and correct.

15. **The radar is a RASTER, so it fetches per instant — but only per instant it has not already decoded.** Every other measured feed loads its day and samples it locally (9). A day of FMI's `suomi_dbz_eureffin` composite is 288 images and ~25 MB against the ~20 kB a day of stations costs, so `radar.ts` cannot load a day. What it does instead is keep what it has: `RadarReel` is a byte-bounded LRU of decoded frames, and the draw picks the newest one within tolerance of the playhead (`reelPick`), exactly as `sampleTimeline` picks a station's nearest reading. That is what makes a scrub track the pointer. **The single-slot design it replaced could not**, and every part of that is worth keeping written down, because each was individually defensible: the fetch target was a trailing-edge `useDebounced`, which by construction never fires while a value keeps changing, so a drag issued *zero* requests until the pointer had been still for 400 ms — and during playback the wait was `ARCHIVE_PLAYBACK_DEBOUNCE_MS`, a constant deliberately chosen so it would never elapse (right for a request that only refines something already drawn, false for the one that *is* the layer). One frame was held, so a backward drag blanked the map on its first step (`radarInRange` refuses a frame ahead of the playhead) and a forward drag froze the rain for 15 simulated minutes and then blanked. And the state machine tracked *camera* coverage rather than *clock* coverage, so through the whole blank scrub it printed "the newest radar composite has not been published yet" over an archive FMI certainly holds. Bound the reel **by bytes and never by count**: `MAX_RADAR_PX` is 1400, so a frame is up to 1400×1400×4 = 7.8 MB decoded and a twelve-slot cache is anywhere between 23 MB and 94 MB depending on whose viewport it is. The fetch is a **pump, not an effect** — one long-lived loop per camera generation, taking one instant at a time from `reelPlan` against the *live* playhead ref, never aborted by the clock moving (an in-flight frame lands in the reel and covers ground a later scrub wants; aborting it is how a stuttering drag threw away every round trip it started). What is still true and must stay: the instant is quantised to the composite's own **five-minute grid**; the frame carries **its own timestamp**, which the readout prints, because FMI publishes a scan minutes after taking it and saying so is the difference between a lag and a lie; the tolerance applies to the **whole frame** (`radarInRange`, 15 min) since a raster has no value to drop; an instant the mosaic does not hold answers **HTTP 200 with a text/xml ServiceException**, so the content type is tested and the answer is `null` rather than a throw — printing that as "could not load" is a lie about a working service, and the reel now *remembers* it (`absent`) instead of re-probing the same four instants on every camera nudge, re-asking only at the leading edge where the answer still changes. Nothing is ever **blended**: two composites cross-faded would draw a rain field nobody measured, which is invariant 8 applied to pixels. The cells are **500 m** (established by run-length over the same box at 250 and 125 m/px), which caps the requested pixel count, and the grey wash FMI's style paints outside the radars' range is **kept** as the publisher's own "we cannot see". Smoothing is on only when the frame is *shrunk*.

15a. **The rain forecast is MET Norway's, because FMI publishes none a browser can read.** Enumerated, twice, so it is not re-investigated: all three `openwms.fmi.fi` workspaces (`Radar`, `Basemaps`, `silva`) hold 116 time-dimensioned layers and **none** reaches past the present minute; the string "nowcast" appears in **0** of the 160 WFS stored query ids; and the forecast *grid* queries resolve to `opendata.fmi.fi/download`, whose actual GET carries **no `Access-Control-Allow-Origin` at all** (the OPTIONS preflight does answer — a passing preflight with a bare response still fails the browser). RainViewer's free nowcast array is empty on every poll and it is an aggregator besides. So past "now" the layer is `thredds.met.no`'s `radarnowcasting` ncWMS (`nowcast.ts`): 1 km, 5-minute steps, **+115 minutes** from its own analysis, NLOD + CC BY 4.0, CORS `*`, no key — and its mosaic node list contains **all eleven FMI radars**, so over Finland it is the forward continuation of the very measurement the page already draws. MET's terms forbid using the name "Yr" or its logo; neither appears. What is forbidden here is the obvious shortcut: **never advect FMI's own composite forward.** A model we wrote, drawn as data, is the one thing this project will not ship. Five things this service does that look like success: an unpublished run answers **HTTP 500 with an 11 kB Tomcat HTML page** (not a ServiceException), `…/radarnowcasting/latest.xml` answers **500** so there is no stable alias and the run must be found by walking the 5-minute grid backwards (~7 min publication latency), an instant past a run's horizon answers **HTTP 400** with a proper ServiceException — an answer, not an error — ncWMS **snaps** a requested time to its nearest step so 08:01 and 08:02 return byte-identical images, and its `<Dimension>` extent is **pretty-printed onto its own indented line**, where `Date.parse("\n            2026-08-18T07:40:00.000Z")` is `NaN` and not a date (that one shipped for an afternoon: every run in the walk looked unpublished and the forecast reported "could not load" against a service answering 200). Two rendering facts: ncWMS paints **every** value including zero unless told `belowmincolor=transparent`, so the floor is ours at 0.1 mm/h — the conventional threshold for measurable rain — and the palette is MET's own `metnoprecipitation`, which is nothing like FMI's cyan dBZ ramp and is what tells the two halves apart on the map without anything invented here. The seam is the **wall clock**: at or before now, FMI; after it, MET. The run's window opens at its own analysis, a few minutes in the past, and that overlap is deliberately never used — "a measurement beats a forecast outright" (9), in raster form. THREDDS asks callers not to open parallel sessions and its GetMap is 1–2 s against FMI's sub-second, hence `RadarReel.forecastInflight`, which holds the forecast to one request at a time while the measured half runs two.

16. **`sunTimes` anchors on the SOLAR day, so ask it at local noon.** `julianCycle` rounds to the nearest solar-noon-centred day at that longitude, and solar midnight at Helsinki is about 01:20 local — so handed the raw playhead instant it answered with *yesterday's* pair for the first eighty minutes of every day. The bar draws sunrise and sunset by position within the day it is showing, so both marks silently vanished off the left end of the track and the readout printed yesterday's day length under today's date. At Utsjoki the previous day can be a different `polar` state entirely. `src/utils/sun.ts` now says so in its own docstring and a test pins it.

17. **Every clock on the page is 24-hour, pinned rather than inherited.** The formatters in `timeControl.ts` take the viewer's locale for month names and field order but pass `hourCycle: 'h23'` — an en-US browser otherwise resolved to h12 and printed "03:30 PM" in the clock chip and "1 AM … 11 PM" along a ruler drawn against a 24-hour track, and `SunStat` reserves sunrise/sunset at 5ch for "00:00", which "05:24 AM" overflows. `hourCycle` and not `hour12: false`: the latter resolves to h24 in some locales (midnight as "24:00"), and passing it alongside would take precedence and undo the fix. `hourLabel` is the one clock that is NOT an `Intl` formatter — asking Intl for a lone hour is exactly where `hour: '2-digit'` is ignored, so the ruler is `String(getHours()).padStart(2,'0')`, which also keeps it right on the two DST days.

18. **The UV index is the page's one MODELLED feed, and the registry has a word for that.** FMI publishes no UV index a browser can ask for — 0 of its 320 stored queries, and `fmi::observations::radiation::*` carries `UVB_U`, a UV-B irradiance in mW/m² at eight stations, which becomes an index only via a conversion *we* would be inventing on top of a measurement of something else. So `uv.ts` takes Copernicus CAMS through Open-Meteo's air-quality API (CC BY 4.0, no key, CORS `*`, 11 km European domain, 92 days back to ~5 days ahead). Its "past" is an earlier run of the same model, so unlike `forecast` there is no measured half to prefer and no join to draw: the `modelled` time model exists to say that, and the readout says model over the whole window. Three things that bite: past the run's horizon the API answers **HTTP 200 with `null`s**, and a null read as 0 draws "the sun is not up" over a day nobody has run — `parseUv` drops them so the strip can say the model does not reach that instant; the request rounds the coordinate to the model's own 0.1° cell (`uvCell`), or the `moveend` camera sync issues a request per pan for a value that cannot have changed; and the tolerance is exactly half the publishing step (30 min), which covers every instant of the day once and never prints an hour under a time nearer the next one. `timeformat=unixtime` keeps a day of both variables under half a kilobyte.

### Sweden (`scripts/se/`, `docs/SWEDEN_EXPANSION.md`)

1. **Area ids are bare and disjoint**: a Finnish postal code `00100`, a Swedish DeSO `0180C1090`. Validate through `src/utils/areaId.ts` (`isAreaId`, `countryOfId`), never a `\d{5}` regex — that silently drops every Swedish id from URLs, notes and favourites. Swedish region ids start `se_`.
2. **Never put the two countries on one scale.** Shared keys (`unemployment_rate`, `ownership_rate`, …) carry SCB's definitions for Swedish areas, documented per metric in `data_sources.json` → `countries.se`. National ranges and national averages are Finland's alone (filtered by `countryOfId`); Swedish views use `stopsSe` (`layerForCountry`) and `layerInCountry` hides layers a country has no data for. Layers counted the same way in both countries (OSM services, Skolverket schools, SILAM air, water proximity) keep Finland's stops instead.
3. **SCB tables carry both DeSO versions**: only `…_DeSO2025` codes match the 2025 boundaries. From 2025 SCB adds cell noise (a part can exceed its total; shares are capped at 100) and suppresses counts of 1–2 as `..`. A share with a suppressed cell is written only when both bounds round to the same published decimal — never imputed (`build_se_geojson.py`).
4. **Region averages need numerators and denominators**: Swedish features carry `se_*` counts and `computeMetroAverages` sums them per country, so a mixed selection never pads a Finnish denominator with Swedish residents.
5. **Profile pages are lean on purpose** (`scripts/prerender-se.mjs`): 6,160 areas × 3 languages = 18,480 pages at ~15 KB, with no social card and no oEmbed, because the published tree's FILE COUNT is what drives deploy time (see the social-card note). `check-dist-size.mjs` budgets were raised to 66,000 files for them; measured 58,936. A per-area Swedish card would add 18,480 files and minutes of rasterizing per deploy — don't add one without re-measuring that. Scripts that read `region_properties.json` (open data, the similar-areas mesh, national ranges) filter to Finland: it carries both countries.
6. **DeSO polygons are cut at the shore** (`scripts/se/clip_deso_land.py`, OSM land polygons; run after `fetch_se_boundaries.py`, before `build_se_geojson.py`). SCB's own polygons follow municipal borders out to sea, so Sweden drew smooth blobs over the Baltic and its region outlines (also the always-on outline line layer in `Map.tsx`) ran out to the maritime border. Lakes stay, as in Paavo. Only display geometry: every area figure comes from SCB's tables.
7. **Country borders are strong only where they touch a country on the map** (`styleBaseBorders` in `src/utils/basemap.ts`, `dataCountries` in App). From zoom 5 the basemap tiles name each side (`adm0_l`/`adm0_r`, ISO alpha-3); **below zoom 5 OpenFreeMap's tiles carry no country codes**, so those zooms draw `src/data/country_borders.geojson` (Natural Earth, `scripts/fetch_country_borders.py`, `maxzoom: 5`) instead. A new country needs its ISO code in `ISO3` and in that script's `COUNTRIES`.
8. **`city=fi` / `city=se` is the national view of one country** (`RegionSelection.country`, `parseCityParam`): `cityFilter` stays `'all'`, the region features and the outline lines are filtered to that country, and `viewCountry` follows it. Picking Finland or Sweden in the region selector sets it; a region pick or World clears it.
9. **The quality index scores each country against itself, then calibrates.** `computeQualityIndices` takes per-country ranges (`getCountryRanges()`: Finland's at `national_ranges.json` → `ranges`, Sweden's at `countries.se.ranges`), reads income from `propertiesSe` (ekonomisk standard), and drops a factor Sweden has no range for (accidents, noise — canopy is the same Copernicus product as Finland's, `scripts/tcd_cdse.py`; crime is Brå's, per municipality and per city district in Stockholm, Göteborg and Malmö, `scripts/se/fetch_se_crime.py` + `fetch_se_districts.py`) rather than scoring it a neutral 50. Under the default weights a Swedish composite is then mapped by quantile onto Finland's (`calibration` curves, `mapQuantile`), because the missing factors are ones most Finnish areas score well on and left the raw Swedish composite ~8 points lower. Area scores share one scale; region averages still lean urban in Sweden until it has those factors. A custom lens is shown uncalibrated. `build_region_aggregates.mjs` must pass the same ranges as the runtime, or the national view and the map disagree.

### Adding a new data layer

1. Add the `LayerId` and a `LayerConfig` to `LAYERS` in `src/utils/colorScales.ts`
2. Add the layer to a group in `LAYER_GROUPS` (`src/components/LayerSelector.tsx`)
3. Add metric metadata in `src/utils/metrics.ts` (`NeighborhoodProperties`, and `METRIC_DEFS` if it needs weighted averaging)
4. Register the source in `src/data/data_sources.json` **and** its vintage in `scripts/provenance.json` — validation fails if they diverge
5. Add labels to **all three** locale files (`fi.json`, `en.json`, `sv.json`) — the key-parity test fails CI otherwise
6. Include the data in `public/data/metro_neighborhoods.geojson` (via `scripts/prepare_data.py`)
7. Rebuild the app artifacts with `npm run build:data`; re-baseline `validate_data.py` if coverage changed intentionally
