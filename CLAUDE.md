# CLAUDE.md

## Project overview

naapurustot is a static React + TypeScript map application for exploring postal-code-level statistics across all of Finland — 3,018 postal-code areas in 69 sub-regions (seutukunnat). Live at naapurustot.fi. The frontend runs entirely in the browser from pre-built TopoJSON/JSON assets; an optional Express + PostgreSQL backend (`server/`) adds accounts and sync of favorites/shortlist/notes/preferences. The app works fully without it.

## Architecture

- **Framework:** React 19, TypeScript 5.9, Vite 8
- **Map:** MapLibre GL JS with lazy-loaded Turf.js modules for geospatial calculations
- **Styling:** Tailwind CSS 3
- **State:** React hooks + Context (theme). No external state library. Tooltips use an external store (`tooltipStore.ts`) to avoid 60 Hz re-renders.
- **i18n:** Finnish (default), English, and Swedish. Translations live in `src/locales/{fi,en,sv}.json` (flat keys, parity enforced by a test). Use `t('key')` from `src/utils/i18n.ts`; `React.memo` components calling `t()` must also call `useI18nVersion()`. en/sv are lazy-fetched assets — never import them statically (bundle budget).

### Key directories

- `src/components/` — React components (Map, NeighborhoodPanel, LayerSelector, Legend, SearchBar, panels, dropdowns; `profile/` for profile-page parts)
- `src/hooks/` — 25 custom hooks (data loading, localStorage+server-synced user state, URL state codec, gestures)
- `src/utils/` — Data layers (`colorScales.ts`, 76 layers), metric definitions (`metrics.ts`), quality index, regions (69), similarity, filtering, formatting, i18n
- `src/locales/` — Translation JSON files (fi.json, en.json, sv.json)
- `src/__tests__/` — 170+ Vitest test files (jsdom)
- `src/data/` — **What the app actually loads** (generated by `npm run build:data`): `regions/*.topojson` (69 per-region files), `seutukunnat.topojson` (region outlines), `region_properties.json` (all 3,018 areas, geometry-stripped), `national_ranges.json`, plus adjacency/coverage/grid manifests
- `public/data/metro_neighborhoods.geojson` — Pipeline output (~39 MB), source of truth for `build:data`; **build input only** — it is stripped from `dist/` at build time and never fetched by the app
- `scripts/prepare_data.py` — Python data pipeline that rebuilds the GeoJSON

## Data integrity

**All data must come from real, verifiable sources.** Never generate, fabricate, or use placeholder/fake data — not in the GeoJSON dataset, not in the data pipeline, and not as temporary stand-ins. If real data is not yet available for a metric or area, leave it out entirely rather than filling in synthetic values. Every value shown on the map must trace back to an actual data source (e.g., Statistics Finland, HSL, Helsinki Region Infoshare, OpenStreetMap).

**Always propagate data into the GeoJSON.** When adding or updating any data layer, verify that the values are written into `public/data/metro_neighborhoods.geojson` — the file `build:data` reads — not just the intermediate JSON in `scripts/`. After updating data, confirm the GeoJSON property values match the new data, then run `npm run build:data` so the change reaches the `src/data/` artifacts the app loads. This step must never be skipped.

## Data granularity

We want the lowest-level data possible. The minimum acceptable granularity is **postal code level**, but whenever a data source offers finer resolution (e.g., 250 m × 250 m grid cells, building-level, block-level, or coordinate-level data), prefer and integrate that instead (see the grid overlays: air quality ~250 m, light pollution ~500 m). When evaluating new data sources or extending existing ones, always check whether a sub-postal-code breakdown is available. Municipality-level values distributed to postal codes must be flagged `is_proxy` in `src/data/data_sources.json` (validation enforces this).

## Git workflow

**Do not create pull requests.** Push your changes to a `claude/*` branch and let the auto-merge workflow (`.github/workflows/auto-merge.yml`) handle merging to main after CI passes. Never open a PR manually or via API. Note: pushing a second `claude/*` branch cancels an in-flight auto-merge run (shared concurrency group) — serialize or stack branches.

### Post-push: verify the auto-merge run (do this every push)

Pushing is not "done" — the merge only lands if all auto-merge jobs (`security`, `checks`, `e2e`, `lighthouse`, `server`) pass. There is no PR and no webhook for branch-push CI, so you must check the run yourself and drive it to green:

1. **Poll the run.** `mcp__github__actions_list` → `list_workflow_runs` for `auto-merge.yml`, `workflow_runs_filter.branch = <your claude/* branch>`. Read `status`/`conclusion` of the newest run (re-poll until `status: "completed"`).
2. **`conclusion: "success"`** → the merge landed and the branch was auto-deleted. Done.
3. **`conclusion: "failure"`** → `mcp__github__get_job_logs` with `run_id`, `failed_only: true`, `return_content: true`. Diagnose, fix on the same branch, re-push, and repeat from step 1 until green (re-pushing the *same* branch is safe; pushing a *different* `claude/*` branch cancels the in-flight run). If a failure is genuinely out of scope or you're stuck after a couple of rounds, stop and report the diagnosis instead of looping.

The container is ephemeral, so verify within the session that produced the push. **Known recurring failure modes:**

- **`security` — `node scripts/check-audit.mjs` / `… server/api`** (`npm run audit:check` locally; run for both trees): a transitive high-severity advisory. Fix by pinning the offending package in that tree's `package.json` `overrides` to the first patched version *within its parent's compatible major* (e.g. `"undici": "^7.28.0"` to satisfy jsdom's `^7.x`), then `npm install` and re-run the gate. Don't jump a major (it can break the parent) — and when the patch exists only in a later major, verify the parents can load it before forcing it: `brace-expansion@5` needed `"minimatch": "^10.2.5"` alongside it, because `minimatch@3` does `require('brace-expansion')` as a callable and v5 exports a namespace. Moderate-only advisories don't fail the gate. If a high advisory genuinely cannot apply to this codebase and its only fix is a major bump, add a reviewed entry to `ALLOWLIST` in `scripts/check-audit.mjs` with the reason, the `scope` (`.` or `server/api`) and an `until` date — the gate fails once an exemption expires, so it can't become permanent.
- **`checks` — build:data idempotency gate**: re-running `npm run build:data` must reproduce committed `src/data`/`public/data` byte-for-byte. A diff means a generator is non-deterministic — it must derive any timestamp/vintage from committed source data, never `new Date()`/`Date.now()` (e.g. the planning snapshot is read from `scripts/planning_raw/snapshot.txt`, stamped by the fetch scripts at fetch time). Fix the generator; only commit a regenerated artifact when the source data genuinely changed.

## Known pitfalls

### Bundle budget

`scripts/check-bundle-size.mjs` enforces **two** budgets (both in `ci.yml` and `auto-merge.yml`); either one over fails the build.

- **`BUDGET` = 324,000 bytes** — the gzipped sum of all app JS except `maplibre-*` and the `/live/` chunk. This is the map's critical path and runs on roughly 1 KB of headroom. Lazy-loading does not exempt code from it.
- **`LIVE_BUDGET` = 24,000 bytes** — the `/live/` realtime sub-app, matched by the `LivePage-` chunk prefix.

The split is by *reachability*, not naming: Rolldown folds a module into the `LivePage-` chunk only when the live route is its sole importer, so anything `/live/` shares with the map still counts against `BUDGET`. Do **not** try to force this with a `manualChunks` group — that was tried and backfired twice (it swallowed the `maplibre` chunk, then magneted ~21 KB of shared modules, understating the map budget). Let the natural chunking do it.

Keep data out of JS: fetch it as a static asset (`?url` imports) like the locales, region files, and adjacency graph do.

### Prerender head-token regexes

`scripts/prerender.mjs` clones `dist/index.html` using first-match regexes over `<title>`, `<noscript>`, and `</head>`. Never put those tokens in index.html's head — even inside comments — or all ~9,000 prerendered pages silently corrupt. Run `npm run build:pages` to catch it.

### All-Finland view: region borders

The all-Finland view (`?city=all`, the default) shows seutukunta outlines, not individual postal-code borders. This has broken repeatedly — do not re-introduce these issues:

1. **Region outlines are pre-baked** into `src/data/seutukunnat.topojson` (built by `scripts/build_seutukunta_boundaries.mjs`) and lazy-fetched at runtime by `src/utils/metroAreas.ts`. Runtime no longer uses `@turf/union` (the `package.json` dependency is vestigial). The degraded fallback while outlines load is raw MultiPolygon concatenation, which preserves internal postal borders — `ensureOutlinesLoaded` must keep resetting its promise on fetch failure *and* on an empty parse, or the view locks onto the fallback permanently.
2. **The `metroAreaCache` must invalidate when outlines become available.** The cache records a `usedOutlines` flag — if it was built with the fallback before the outlines fetch resolved, it must be rebuilt once they are ready. Do not remove or simplify this check.
3. **Both `Map.tsx` and `SplitMapView.tsx` must filter out postal-code borders for region features** using the `_isMetroArea` property: `METRO_LINE_LAYER` draws only the outer region boundary; the regular `LINE_LAYER` (and the no-data hatch layer) must exclude `_isMetroArea: true` features.
4. The all-cities dataset (`loadAllData`) has `geometry: null` on every feature — code that assumes geometry there (flyTo, centroids) must guard for it; national-scope features navigate to profile pages instead of flying the map.

### MapLibre

- Never replace a state-dependent paint expression with a constant (`setPaintProperty`) — the next `setFeatureState` throws. Hide layers via `buildFillOpacity(0)`.
- Gate post-init layer work on the persistent `mapStyleLoadedRef`, not `map.isStyleLoaded()` (returns false during in-flight `setData` re-parses, silently dropping work).

### Adding a new data layer

1. Add the `LayerId` and a `LayerConfig` to `LAYERS` in `src/utils/colorScales.ts`
2. Add the layer to a group in `LAYER_GROUPS` (`src/components/LayerSelector.tsx`)
3. Add metric metadata in `src/utils/metrics.ts` (`NeighborhoodProperties`, and `METRIC_DEFS` if it needs weighted averaging)
4. Register the source in `src/data/data_sources.json` **and** its vintage in `scripts/provenance.json` — validation fails if they diverge
5. Add labels to **all three** locale files (`fi.json`, `en.json`, `sv.json`) — the key-parity test fails CI otherwise
6. Include the data in `public/data/metro_neighborhoods.geojson` (via `scripts/prepare_data.py`)
7. Rebuild the app artifacts with `npm run build:data`; re-baseline `validate_data.py` if coverage changed intentionally
